# Agent Instructions — Sky House Cleaning Website

Coding-specific instructions for Claude (and other agents) working in this Astro project. These override default agent behavior.

## Never run npm commands

Do not run `npm install`, `npm run dev`, `npm run build`, `npm run preview`, or any other npm/node command in this project — for any reason, including "verifying" or "testing" changes.

- Builds are handled by Vercel on deploy. There's no need to run `npm run build` to check for errors.
- The dev server (`npm run dev`) is already running locally on my machine. You don't need to start it.
- If you want to sanity-check a change, do it by reading the files (syntax, structure, matching patterns already used elsewhere in the codebase) — not by running a command.

## Git

Claude handles git for this project — add, commit (with clear descriptive messages), and push to `origin/main` as work is completed. No need to ask before committing/pushing normal in-progress work.

## Booking & payments architecture

The site has a full booking flow, in order:

1. **Pricing page** (`src/components/PricingConfigurator.astro`) computes a quote client-side and encodes the customer's raw selections into `/book?s=<json>`.
2. **`/book` page** (`src/pages/book.astro`) shows that quote, and has its own date/time picker (Step 1 — a date strip + time-slot grid, calling `src/pages/api/availability.js` which reads real availability from Google Calendar via `src/lib/googleCalendar.js`) plus an on-site contact form (Step 2 — name, email, phone, address, access/gate code, pets, notes). No Google-hosted form is shown to the customer.
3. Submitting POSTs `{ selections, customer, slot }` to `src/pages/api/create-checkout-session.js`, which re-validates the slot is still free, recomputes the price authoritatively (see below), and creates a Stripe Checkout Session — all the customer/slot details ride along as Stripe metadata.
4. Stripe redirects the customer to pay. **Only after payment actually succeeds**, Stripe calls `src/pages/api/stripe-webhook.js`, which reads that metadata and creates the *real* Google Calendar event (via `createBookingEvent` in `src/lib/googleCalendar.js`) — title, description with every detail from the form, at the exact picked time. This is deliberately webhook-triggered rather than done immediately on "Continue to Payment," so an abandoned checkout never holds a calendar slot.

Important: the price shown in the URL/order summary is **never trusted for the actual charge**. `src/lib/pricing.js` (`calculatePrice()`) re-derives the price server-side from `src/data/content.js` on every checkout request, so the amount charged always matches the site's real pricing data, even if someone tampers with the URL.

### Recurring billing (subscriptions)

Weekly / bi-weekly / monthly **standard** cleanings are real Stripe subscriptions, not one-time charges — the card is saved and future visits bill automatically. One-time, deep clean, and move-in/out are always single payments.

- `src/lib/pricing.js` exports `RECURRING_INTERVALS` (the Stripe billing interval + how many days/months apart each plan's visits are) and `isRecurringFrequency()`.
- `src/pages/api/create-checkout-session.js` creates the Checkout Session with `mode: "subscription"` for recurring plans. All line items (base service **and** add-ons) are included as real recurring Checkout line items, plain — no special tagging or handling. On a recurring plan, picking an add-on (e.g. inside oven, inside blinds) means it's part of *every* visit going forward, not just the first one: the customer is charged for it every cycle, and staff clean it every time. `PricingConfigurator.astro` states this plainly next to the price and in the add-ons section itself before checkout, so it's never a surprise.
  - **This was not the first design, and the earlier one shouldn't be reintroduced.** An earlier version tried to make add-ons apply (and bill) only once, for the first cleaning, on the theory that "clean my oven this one time" is what most customers picking a recurring plan actually want. Three real problems killed that approach, each confirmed live, not just in theory — worth knowing so nobody re-attempts it the same way:
    1. Making add-ons one-time Checkout line items outright fails: Stripe rejects combining any one-time price with `proration_behavior: "none"` (the mechanism that defers the subscription's first charge to the actual cleaning date, see "Billing date alignment" below) — `"You cannot set 'proration_behavior' to 'none' in a Checkout Session with one-time prices."` This applies to `optional_items` too, not just `line_items` — it's a property of how the session invoices, not which field the price came from.
    2. Adding add-ons as pending invoice items (`stripe.invoiceItems.create`) after the subscription exists avoided that error, but the Checkout page's own total then didn't include them (Stripe doesn't know about charges added after the session is created) — the customer would authorize a lower amount than what actually got charged.
    3. The version that finally avoided both of the above — real recurring add-on line items that get silently removed via `stripe.subscriptions.update({ items: [...].map(id => ({ id, deleted: true })) })` right after the first invoice fires — got the total right, but Stripe's own Checkout page prints a fixed per-line caption like "Billed weekly — $20.00/week after" on every recurring line item that can't be turned off or reworded, so it read as though the add-on would keep billing forever even though it wouldn't. Layering `custom_text` disclaimers and relabeling the add-on's name on top of that got the numbers technically correct but never actually stopped looking confusing on Stripe's own page — which is what led to abandoning one-time add-ons altogether in favor of the current, much simpler "add-ons just recur too" model.
  - The customer/slot metadata is duplicated onto `subscription_data.metadata` (including `lastVisitStart`/`lastVisitEnd`, seeded to the first picked slot) — this is what lets the webhook figure out future visit dates, since Stripe doesn't automatically carry Checkout Session metadata onto the subscription or its invoices.
- `src/pages/api/stripe-webhook.js` handles `invoice.paid`: for the first billing cycle (`billing_reason: "subscription_create"`) it does nothing, since `checkout.session.completed` already created that first calendar event. For renewals (`billing_reason: "subscription_cycle"`) it computes the next visit's date/time (same day-of-week/time as the last one, advanced by the plan's interval), creates that calendar event, and updates the subscription's `lastVisitStart`/`lastVisitEnd` so the cycle after that computes correctly too.
- `src/pages/book/success.astro` creates a Stripe Billing Portal session for subscription bookings and shows a "Manage Your Subscription" link/button, so customers can update their card, view invoices, or cancel without calling in.

**Two one-time Stripe Dashboard steps this needs** (do these in **both** test and live mode):

1. **Turn on the Customer Portal** — Settings → Billing → Customer portal → configure and save (defaults are fine to start: allow canceling, updating payment method, viewing invoices). Until this is turned on, the "Manage Your Subscription" link just won't appear (fails silently) rather than breaking the booking confirmation.
2. **Add `invoice.paid` to the registered webhook** — Developers → Webhooks → your endpoint → Edit destination → add `invoice.paid` alongside the existing `checkout.session.completed`. Without this, recurring visits after the first one won't get scheduled (the customer will still be charged correctly by Stripe either way — this only affects whether the follow-up calendar event gets created automatically).

Known limitation: monthly plans advance by calendar month, so a visit booked for the 31st can land on the 1st–3rd of the following month depending on how many days that month has. Rare in practice, but worth knowing about.

### Booking a phone customer (staff tool)

`/admin/quote` → `/admin/book` is the staff-side path for someone who calls in instead of booking online — password-protected the same way as `/admin/reschedule`.

- **`src/pages/admin/quote.astro`** just renders the same `<PricingConfigurator />` component the public Pricing page uses (same catalog, same prices, so staff and customers always see identical numbers), with its `ctaHref` pointed at `/admin/book` instead of the public `/book`.
- **`src/pages/admin/book.astro`** is a close copy of the public `/book.astro` — same date/time slot picker (including the month-grouped date strip with prev/next month arrows, and the collapsible full-calendar toggle below it, both ported from `/schedule.astro`), same contact form, same `/api/availability` endpoint, unchanged. Staff go through the exact same slot-conflict checking a customer would. Also has a `min-width: 0;` fix on `.book-main`/`.book-summary` (same fix `/schedule.astro` needed) so the wide date strip can't force the page to scroll horizontally.
- **The one real difference, and the reason this needed its own page instead of just reusing `/book.astro`:** there's no code anywhere in this app (and deliberately no plan to add any) that collects a card number without the cardholder completing Stripe's own hosted Checkout page themselves — no `PaymentIntent`, no manually-keyed card, no Stripe Payment Links. That's a deliberate choice: keying in someone's card over the phone would pull Sky House into a meaningfully bigger PCI compliance burden (a stricter self-assessment questionnaire with Stripe) for a solo/small-team operation, when the actual need is just "get this customer a way to pay." So instead of `window.location.href = data.url` (the public page's behavior) or creating a Stripe session directly, `/admin/book.astro` submits to `/api/admin/create-pending-booking.js` and displays a link to the public `/confirm/[id]` page — a copy-link button and an "Open Confirmation Page" link — for staff to text or email to the customer. See "Phone booking confirmation link" below for why it's a confirmation link and not a direct payment link (the short version: a checkbox on this screen would only prove staff clicked it, not that the customer agreed to anything). **Nothing is booked or charged until the customer reviews it, confirms, and completes payment themselves.**
- No changes to the webhook's core booking logic were needed for this — the confirmation flow calls the same, already-hardened `create-checkout-session.js` handler underneath (see "Phone booking confirmation link"), just with an extra human-confirmation step in front of it instead of going straight from staff's screen to Stripe.

### Rescheduling recurring plans

Two different situations, handled two different ways:

- **One-time reschedule (reverts back automatically afterward)** — e.g. moving just next week's visit to a different day, then back to normal after that. Just edit that one event directly in Google Calendar (drag it, or edit the date/time). Don't touch anything in Stripe. The subscription's stored schedule (`lastVisitStart`/`lastVisitEnd` in its metadata) is what every future visit is computed from, and it's never affected by manually moving a calendar event — so the cycle after the one you moved automatically lands back on the regular day.
- **Permanent reschedule (every future visit shifts)** — e.g. moving a customer from Tuesdays to Wednesdays going forward. Use the staff tool at `/admin/reschedule` (password-protected — see below). Find the customer, pick the new date/time, and save. This updates both the subscription's stored schedule *and* moves their current upcoming calendar event to match, so it takes effect immediately.
  - **Three ways to find the customer**, all landing on the same result card/cancel-actions UI: the original email search; a **name dropdown** (`#customer-select`) listing every active plan; and a **mini month calendar** (`#cal-grid`) showing each plan's next scheduled visit as a clickable chip, since a recurring plan's `lastVisitStart` metadata *is* its only meaningful upcoming date (the same event just moves forward each cycle — see "Dispatcher" below for why). The dropdown and calendar are both populated from a single `/api/admin/list-subscriptions.js` fetch on page load (same Stripe query shape as `/admin/minimum-commitments`, reusing `find-subscriptions.js`'s per-subscription field shape) — selecting either calls the page's existing `renderResults([sub])` directly, no extra round trip. The calendar deliberately reads from Stripe subscription metadata, not real Google Calendar events, since calendar events have no link back to a subscription id today.
  - **`reschedule.astro`'s `<style>` is `is:global`, not Astro's default scoped styling** — this page (like `admin/dispatch.astro`) builds its customer cards and now its calendar cells/chips client-side via `document.createElement`, and Astro's scoped-CSS attribute is only applied to elements written directly in the page template, not ones created by client JS. A scoped `<style>` here would silently fail to style any of that dynamic markup.

Neither of these changes when the customer is actually billed — visit date/time and billing date are tracked separately.

**Staff tools setup:** `/admin/*` and `/api/admin/*` are gated by HTTP Basic Auth (`src/middleware.js`), using the `ADMIN_USERNAME`/`ADMIN_PASSWORD` env vars — pick your own values (not tied to any Google/Stripe account) and set them in `.env` locally and in Vercel's Production environment variables. Until both are set, those routes return a 503 instead of prompting for a login.

### Canceling recurring plans

`/admin/reschedule` also has four cancel actions per customer, each calling its own API route:

- **Cancel Next Visit — Still Charge** (`/api/admin/cancel-visit.js`) — removes just the upcoming calendar event. Billing and every visit after that continue completely normally — since billing is anchored to the actual cleaning date (see below), the customer is still charged on that original date even though nothing happens on the calendar. Nothing about the subscription's stored schedule changes. Use this for a late cancellation where the plan's cancellation policy still applies (e.g. short-notice vacation).
- **Cancel Next Visit — Skip Charge** (`/api/admin/skip-visit.js`) — cancels the upcoming visit *and* the charge for it. Since billing is tied to the cleaning date, "don't charge for the skipped visit" means fast-forwarding the whole plan by one interval: the currently-scheduled calendar event is moved to the *following* visit's date (using the same interval math the renewal webhook uses), the subscription's stored `lastVisitStart`/`lastVisitEnd`/`lastEventId` are updated to match, and billing is re-anchored to that same new date via the `trial_end` mechanism (see "Billing date alignment" below) with `proration_behavior: "none"` so the skipped cycle is never invoiced. The day-of-week/time pattern is preserved automatically. Use this for an approved, no-charge skip (e.g. the customer is out of town and it's within the plan's free-reschedule terms).
- **Cancel Plan — On This Date** (`/api/admin/cancel-subscription.js`, `immediate: false`, `cancelDate`/`cancelTime`) — staff pick exactly when the plan should stop. Visits keep billing normally, right on schedule, up through that date; nothing after it. The date/time fields default to right after the currently-scheduled next visit (`afterNextVisitStart`, computed by `find-subscriptions.js` via `nextVisitWindow`), so the common case — "let the already-scheduled visit happen and bill, then stop" — is just accepting the default. Staff can pick a later date to let several more visits bill first, or an earlier one to end things sooner.
  - **Why not `cancel_at_period_end`?** This tool used to offer a simpler "after current period" button using Stripe's `cancel_at_period_end`. That was wrong for this app: because billing is anchored to each visit's actual cleaning date, the subscription's "current period" boundary *is* the next unbilled visit's charge date — so `cancel_at_period_end` canceled the plan right *before* that next charge fired, silently skipping the visit everyone assumed would still happen and get paid for (true for the very first cycle and for every cycle after that, since periods here always run from one charge date to the next). Do not reintroduce `cancel_at_period_end` for this reason — use an explicit `cancel_at` timestamp (see `cancel-subscription.js`) instead, which lets staff choose precisely how many more visits should still bill first.
  - If the chosen date lands on or before the currently-scheduled next visit, that visit will never actually be billed under the new cancellation date — so `cancel-subscription.js` automatically deletes its calendar event too (surfaced to staff as a non-error `note` in the response), rather than leaving an unpaid visit sitting on the calendar.
- **Cancel Plan — Immediately** (`/api/admin/cancel-subscription.js`, `immediate: true`) — cancels the subscription right away *and* deletes the upcoming calendar event, since that visit is being called off. If it was already paid for, issue a refund by hand in the Stripe Dashboard (Payments → find the charge → Refund) — this tool doesn't do that automatically, since not every cancellation should be refunded.

All four require finding the subscription first via the email search at the top of the page, same as rescheduling.

### Minimum-commitment tracking

Every recurring membership has a minimum-commitment term defined in its policy (see `Policies/Recurring Cleaning - <Frequency>.md` in the top-level project vault — all three frequencies now written: weekly 8, bi-weekly 4, monthly 3 completed visits). There's deliberately no automated block on canceling early — staff decide by hand whether an early cancellation triggers the policy's "responsible for remaining payments" clause, using the count `/admin/reschedule` shows on each subscription's card, or the full-roster view at `/admin/minimum-commitments`.

- **How the count works:** `subscription.metadata.completedVisitCount` increments in `stripe-webhook.js`'s `invoice.paid` handler, once per successful invoice on that subscription — covering both `billing_reason: "subscription_create"` (the delayed first charge) and `subscription_cycle` (every renewal after that, including the `alreadyScheduled` case that fires right after a staff reschedule/skip re-anchors billing). One paid invoice = one visit, whether or not that invoice happened to need a new calendar event.
- **What counts, including a deliberate choice here:** any visit the customer was actually billed for counts, whether or not it was performed. `cancel-visit.js` ("Cancel Next Visit — Still Charge") removes the visit's calendar event but sets no flag and leaves billing untouched — the invoice still comes through and the webhook counts it normally, since the customer paid for that visit (Johnny's call: "they paid for it, it counts," even though the cleaning itself didn't happen). This is a change from an earlier version of this feature, which excluded still-charged-but-uncompleted visits from the count — don't reintroduce that exclusion.
- **What doesn't count:** `skip-visit.js` ("Cancel Next Visit — Skip Charge") never generates an invoice for that visit in the first place, so it's naturally excluded — no flag needed. `cancel-subscription.js`'s auto-delete-on-cancellation-date path is the one remaining place that still sets `metadata.nextVisitCanceled = "true"`, purely as a defensive measure for a visit whose calendar event was removed because it falls on or after a scheduled cancellation date — that invoice isn't expected to ever fire at all once `cancel_at` precedes it, but if timing somehow lets it through anyway, the webhook checks the flag and excludes it rather than counting it (then clears the flag either way, so it never lingers and suppresses a later, unrelated cycle).
- **Idempotency:** Stripe can redeliver the same webhook event. `metadata.lastCountedInvoiceId` records the last invoice id already tallied, so a retried `invoice.paid` for the same invoice never double-counts.
- **Where staff see it:** `find-subscriptions.js` returns `completedVisitCount` and `minimumCommitment` (looked up from `MINIMUM_COMMITMENT` in `src/lib/policies.js` — currently `{ weekly: 8, biweekly: 4, monthly: 3 }`, all three now written) per subscription; `/admin/reschedule`'s `commitmentLabel()` renders it as "Completed visits: X of Y — Z more to go" (or "minimum commitment met"), for one customer looked up by email at a time. `src/lib/policies.js` is the single source of truth for this map — also used by the checkout flow (see "Booking policies at checkout" below) — don't duplicate it elsewhere.
- **Full roster view:** `/admin/minimum-commitments` lists every active recurring plan at once (no email search — it's the whole customer list), sorted with in-progress customers first (soonest-to-finish at the top) and customers who've already met their minimum sunk to the bottom. Unlike `find-subscriptions.js`/`reschedule.astro`, which fetch client-side from an API route, this page queries Stripe directly in its own frontmatter (`prerender = false`, so it runs per-request) since there's no search input to wire up — just "load everything." Currently reads a single page of up to 100 subscriptions (`stripe.subscriptions.list({ limit: 100 })`, no pagination) — fine while the business is this size, but revisit with `autoPagingEach` if the active-plan count ever approaches that.
- **Notification when a customer qualifies:** the instant `completedVisitCount` crosses a plan's `MINIMUM_COMMITMENT` threshold, `stripe-webhook.js` calls `createReminderEvent()` (`src/lib/googleCalendar.js`) to drop a short reminder event on the business calendar — reusing the same Google Calendar credentials/calendar as real bookings, so no new email/SMS service was needed. It fires exactly once per subscription, guarded by `metadata.commitmentNotified`. This is purely a heads-up, not an automatic unlock: self-cancel stays staff-only (see "Self-cancel" decision below) — Johnny still processes the cancellation by hand via `/admin/reschedule` once a customer who's qualified actually asks. If `createReminderEvent()` fails for any reason, the webhook logs it and moves on rather than failing the whole invoice-processing step — `/admin/minimum-commitments` is the fallback way to check who's qualified if a reminder is ever missed.
  - **Privacy:** this reminder lands on the same calendar as real cleaning jobs (`GOOGLE_CALENDAR_ID`), which is shared with cleaning staff so they can see their schedule — but unlike a booking event, its title/description carries a customer's name/phone/address as a note meant for Johnny only, not a job detail cleaners need. `createReminderEvent()` sets `visibility: "private"` on the event for exactly this reason: anyone else with access to that calendar (i.e. staff) sees it only as an opaque "Busy" block with no title or description, while it still shows in full for Johnny. It never reaches customers at all — no attendees are ever added to it, unlike real booking events.
  - **Doesn't block real availability:** `createReminderEvent()` also sets `transparency: "transparent"` — without it, this event (a normal ~15-minute block starting almost immediately) would count as "busy" for `getAvailableSlots`'s freebusy query, the same mechanism that powers every real booking's availability check. `transparent` makes freebusy queries ignore it entirely, so it can never coincidentally block a same-day customer from booking that exact slot.
- **Self-cancel is deliberately staff-only, not automated.** Considered building true self-service (a persistent "manage my subscription" page plus a second Stripe Customer Portal configuration with cancellation enabled, swapped in once a customer qualifies) but decided against it — Johnny wants to keep approving/processing every cancellation himself even after the minimum is met, so the existing admin cancel tools already fully cover this with no further build needed. Don't build the dual-portal-configuration approach unless this decision changes.

### Booking policies at checkout

Every bookable service has a policy page customers must read and check a box agreeing to before paying — a clickwrap consent pattern, not just a footer link. This is deliberate, not decorative: for recurring plans it's also where the minimum-commitment term (see above) is disclosed plainly, before the customer commits.

- **`src/lib/policies.js`** is the single source of truth mapping a booking's `type`/`frequency` to the policy that governs it: `MINIMUM_COMMITMENT` (`{ weekly: 8, biweekly: 4, monthly: 3 }`), `RECURRING_POLICIES`, `ONE_TIME_POLICIES`, and a `policyFor({ type, frequency })` lookup. Used by `create-checkout-session.js` (server-side), `book.astro` (client-side, see below), and `find-subscriptions.js` (admin display). Update the policy text/paths/commitment numbers here, not in multiple places.
- **Policy pages** live under `src/pages/policies/` (`one-time-standard-cleaning`, `deep-cleaning`, `move-in-move-out-cleaning`, `weekly-membership`, `biweekly-membership`, `monthly-membership`), rendered through the shared `src/layouts/PolicyLayout.astro`. The three membership pages each combine the general recurring-plan terms (skip policy, rescheduling, late cancellations, no-shows, booking/availability, failed payments) with that frequency's own minimum-commitment and billing sections into one document — matching what the customer actually agrees to in one place, rather than splitting it across a general page and a frequency page. Source/master copy for all of these lives in the top-level project vault under `Policies/` — that's where Johnny edits policy text; these pages are the published copy and need to be kept in sync by hand when the vault changes.
- **`book.astro`** computes which policy applies right after rendering the order summary and shows a required (unchecked-by-default) checkbox next to a link to that policy, plus — only when the plan has a minimum commitment — a plainly-worded callout stating the number of completed cleanings required before they can cancel. Submitting the form without checking the box is blocked client-side with an inline error, same pattern as the existing "pick a date/time first" check.
  - **Why `define:vars` instead of a client-side `import`:** `book.astro` is a statically prerendered page (the customer's `?s=` selections only exist client-side, parsed from `window.location.search` after load — nothing about the selected service can be known in frontmatter). There's no existing precedent anywhere in this codebase for a plain page `<script>` tag doing a client-side ES module `import`, and since `npm run build`/`dev` can never be run to verify one would actually compile (see the no-npm rule above), the script instead receives `RECURRING_POLICIES`/`ONE_TIME_POLICIES`/`MINIMUM_COMMITMENT` as serialized data via Astro's `define:vars` — the same proven pattern `PricingConfigurator.astro` already uses — and reimplements the small `policyFor()` lookup inline using that data, rather than importing the function itself.
- **Server-side enforcement:** the client-only checkbox state is never trusted as proof of consent. `create-checkout-session.js` re-derives the applicable policy from `selections` via `policyFor()` (same defense-in-depth pattern as price, which is also always re-derived server-side) and rejects the request with a 400 if a policy applies but `policyAgreed !== true`. On success, `policyPath`, `policyLabel`, and a `policyAgreedAt` timestamp are written into `bookingMetadata` (and therefore onto the Checkout Session and, for subscriptions, the subscription itself) — a durable, auditable record in Stripe of which policy version was agreed to and when, in case consent is ever disputed.
- **`/admin/book.astro` doesn't have this checkbox, and deliberately never will** — staff fill that form out over the phone, so a checkbox there would only prove the staff member clicked it, not that the customer agreed to anything. See "Phone booking confirmation link" below for how consent is actually captured for phone bookings.
- **Out of scope:** Car Detailing and Garage/Home Organization aren't sold through this checkout flow (`calculatePrice()` only handles `type: "standard" | "deep" | "moveInOut"`), so they have no policy page here yet.

### Phone booking confirmation link

Staff can't click a policy checkbox on a customer's behalf and have it mean anything — it would only prove the staff member agreed, not the customer. Rather than relying on a staff attestation checkbox or a recorded call (California is an all-party-consent state for call recording, Penal Code 632 — a real legal/disclosure burden for not much evidentiary payoff), `/admin/book.astro` instead hands the customer a link and makes THEM the one who reviews the booking and checks the box. This mirrors how Jobber (Quote Approvals), Housecall Pro, and ServiceTitan (Online Estimates) all handle remote/phone consent — a secure link the customer opens and accepts themselves, not a staff-side attestation.

- **`src/lib/pendingBookings.js`** — Firestore `pendingBookings` collection. `createPendingBooking({ selections, customer, slot })` stores the phone booking as `status: "pending"` with a 7-day `expiresAt` and returns the new doc id. `getPendingBooking(id)` reads it back. `markPendingBookingConverted(id, { stripeSessionId })` flips it to `status: "converted"` once the customer actually pays. There's no third "expired" status written anywhere — expiry is just checked against `expiresAt` at read time, so nothing has to sweep old docs.
- **`/api/admin/create-pending-booking.js`** (staff-only) — what `/admin/book.astro`'s submit button now calls instead of `/api/create-checkout-session` directly. Validates the same required fields, re-checks the slot is still free, stores a `pendingBooking`, and returns `{ id, confirmUrl }` where `confirmUrl` is `/confirm/<id>`. Staff copy/text/email that link to the customer — nothing is booked or charged yet.
- **`/confirm/[id].astro`** (public, no admin auth) — the page the customer opens. Server-rendered: looks up the `pendingBooking` directly via the Firebase Admin SDK in frontmatter (same pattern `/schedule/success.astro` uses to look up a Stripe session server-side), so there's no separate public "get pending booking by id" API to expose. Shows the appointment time, the customer's own entered details (so they can catch a typo and call in before paying), the order summary, and — if `policyFor()` says one applies — the exact same required policy checkbox pattern as the public `/schedule.astro` flow. Handles three dead-end states inline (not found, already converted, expired past `expiresAt`) by showing a message and a phone number instead of the form.
- **`/api/confirm/finalize-pending-booking.js`** (public, no admin auth — this is the endpoint the customer's own browser calls) — validates the `pendingBooking` isn't expired/already-converted and that `policyAgreed === true` was actually sent, then calls `create-checkout-session.js`'s exported `POST` handler **directly as a function** (a synthetic `Request` is constructed and passed in — no network round trip) rather than duplicating its pricing/metadata/slot-check logic. This guarantees a phone booking goes through the exact same server-side price recomputation and slot-conflict check a customer typing their own card number would. The synthetic request includes `pendingBookingId` in its body, which `create-checkout-session.js` writes into the Stripe session's metadata (an additive field, along with `sessionId` on its response — every existing caller only ever read `data.url`, so neither addition could break them). This endpoint then returns the Stripe URL for the customer's browser to redirect to.
  - **Deliberately does NOT mark the `pendingBooking` converted itself** — a Checkout Session existing only means the customer clicked Confirm and got redirected to Stripe, not that they actually paid. An earlier version of this file did mark it converted right here, which caused a real bug: if a customer abandoned checkout (hit the browser back button, closed the tab, had a card declined), the link would permanently show "already confirmed and paid for" even though nothing was ever charged, with no way to retry. Fixed by moving the conversion entirely into `stripe-webhook.js`'s `checkout.session.completed` handler, which reads `metadata.pendingBookingId` and calls `markPendingBookingConverted` there — the one place the whole codebase already treats as "the customer actually paid" (it's also where the real calendar event gets created). Until that webhook fires, the `pendingBooking` just stays `"pending"`, so re-opening the same confirm link after an abandoned checkout lets the customer simply try again.
- **`create-checkout-session.js`'s `cancel_url` is conditional on `pendingBookingId`.** Stripe Checkout has its own "‹ Back" link (distinct from the browser's back button) that sends the customer to whatever `cancel_url` the session was created with. For the public flow this is the generic `/schedule/canceled` page (whose "Back to Booking" link points at `/booking`), but that page is wrong for a phone booking — the customer never touched `/booking`, so that link would strand them. When `pendingBookingId` is present, `cancel_url` is set to `${origin}/confirm/${pendingBookingId}` instead, sending them right back to their own still-`"pending"` confirm page so they can simply try again.
- **Known tradeoff, accepted deliberately:** there's no formal "hold" on a time slot between staff creating the pending booking and the customer actually confirming — the slot-free check happens at creation time (in `create-pending-booking.js`) and again right before the real Stripe session is created (inside `create-checkout-session.js`, called from `finalize-pending-booking.js`), same as the public flow's existing race-window handling. If someone else takes that slot in between, the customer sees `create-checkout-session.js`'s existing "that time was just booked by someone else" error on the confirm page and has to call back for a new time. A longer-lived hold (e.g. a temporary calendar block) was considered and rejected as overkill for a low-volume, one-or-two-staff operation — worth revisiting only if double-bookings from this gap actually start happening in practice.
- **Not yet built:** no admin-side list/dashboard of outstanding pending bookings (e.g. "3 confirmation links sent, none opened yet") — staff currently only know a link went out because they just sent it. Would be a natural small addition if it turns out staff need to follow up on unconfirmed links.

### Billing date alignment

Customers are charged **on the day of each actual cleaning**, not on the day they signed up:

- At checkout, `subscription_data.billing_cycle_anchor` (in `create-checkout-session.js`) is set to the first picked slot's timestamp, with `proration_behavior: "none"` — Stripe generates no invoice at all until that date, so the first real charge lands exactly on the first cleaning, and every renewal after that follows the same cadence from that anchor.
- When staff permanently reschedules a plan via `/admin/reschedule`, `reschedule-subscription.js` also re-anchors billing to the new date using the `trial_end` mechanism (the only way Stripe allows moving an *existing* subscription's billing date to an arbitrary future timestamp — setting `billing_cycle_anchor` directly only works at creation). This briefly shows the subscription as **"Trialing"** in the Stripe Dashboard until that date arrives — expected and harmless, not an error.
- `stripe-webhook.js`'s renewal handler has a belt-and-suspenders check comparing each `invoice.paid` event's billing period to the subscription's stored `lastVisitStart`, skipping calendar event creation if they match — this prevents a duplicate visit from ever being created for a charge that corresponds to a visit already on the calendar (e.g. the delayed first charge, or the charge right after a reschedule).
- **Gotcha for future changes:** because charges are anchored to visit dates, a subscription's Stripe "current period" boundary is always the next unbilled visit's charge date — never a period the customer has already paid through in the usual SaaS sense. Don't use `cancel_at_period_end` anywhere in this app (see "Canceling recurring plans" below for why) — it cancels *before* that next charge fires, not after. Use an explicit `cancel_at` timestamp instead whenever a cancellation needs to let a specific number of future visits still bill first.
- **Another gotcha, found via live testing:** any code path that deletes a subscription's calendar event (`deleteBookingEvent`) must also clear that subscription's `lastEventId` metadata to `""` afterward (`cancel-visit.js` already did this; `cancel-subscription.js` didn't, and got fixed). If it isn't cleared, the next tool that reads `lastEventId` (`skip-visit.js`, `reschedule-subscription.js`) thinks a live event still exists and calls `updateBookingEvent` (a PATCH) on it instead of creating a fresh one. A PATCH against an already-deleted event can succeed at the API level while the event stays in a hidden "cancelled" tombstone state — no error, but nothing ever shows up on the calendar. Two defenses are in place now: (1) every place that deletes an event clears `lastEventId` right after, and (2) `updateBookingEvent` itself throws if the patched event comes back with `status: "cancelled"`, so `skip-visit.js`/`reschedule-subscription.js` catch that and fall back to `createBookingEvent` even if a stale id slips through some other way (e.g. a staff member deleting an event by hand in Google Calendar instead of using the tools).
- **Not a bug, but worth knowing:** if a visit's time on the calendar ever looks off by exactly an hour from what the admin tool or Stripe metadata says, check the viewer's own Google Calendar display timezone (Settings → General → Time zone) before assuming there's a code problem. Everything in this app is computed and stored in `America/Los_Angeles` (matching the Bay Area business hours), but Google Calendar renders events in the *viewer's account* timezone — if that's set to something else (e.g. Mountain, exactly one hour off from Pacific in summer), events will visibly display an hour later even though the underlying stored time is correct. Confirmed via Vercel function logs during testing: the stored/sent timestamps were correct the whole time.
- **Third gotcha, also found via live testing:** `find-subscriptions.js` used to search `stripe.subscriptions.list({ status: "active" })`. Since re-anchoring billing (via `trial_end`) puts a subscription into `"trialing"` status until that date arrives — which happens after *every* `skip-visit.js` or `reschedule-subscription.js` call — an active-only search made staff unable to find a plan right after using those tools. Fixed to `status: "all"`, filtering out only `"canceled"` and `"incomplete_expired"`. The admin UI now also shows a subscription's status next to its schedule whenever it isn't plain `"active"` (e.g. "Status: Trialing (billing date was just re-anchored — expected, not an error)"), so this doesn't look like a mystery next time.

### Live Google reviews

`/reviews` can show real, live Google reviews instead of (or alongside) the hand-picked testimonials in `src/data/content.js`, via `src/lib/googleReviews.js`.

- **How it decides what to show:** `reviews.astro` is `prerender = false` (fetches fresh on every request, not baked in at deploy time) and calls `isConfigured()` first — true only when both `GOOGLE_PLACES_API_KEY` and `GOOGLE_PLACE_ID` are set. If configured, it calls `getGoogleReviews()`; on any failure (bad key, quota, network blip, zero reviews returned) it catches the error, logs it, and silently falls back to the curated `testimonials` array — the page never breaks or shows an error state to a visitor over this. Until Johnny does the one-time setup (see "What I still need to do" below), it behaves exactly as it did before this feature existed.
- **Which API, and why:** uses **Places API (New)**'s Place Details endpoint (`https://places.googleapis.com/v1/places/{placeId}`, auth via `X-Goog-Api-Key` header, fields chosen via `X-Goog-FieldMask: id,displayName,rating,userRatingCount,googleMapsUri,reviews`) rather than the legacy Places API — this is the version Google Cloud Console currently pushes for new setups. Google's response caps at 5 reviews and *Google* decides which ones — not configurable, and not something to work around (Google Maps Platform's content policies require showing review content unaltered, not cherry-picked, so every review returned is displayed, in the order given, with no re-sorting or filtering here).
- **Caching:** a module-level in-memory cache (`CACHE_TTL_MS`, 1 hour) in `googleReviews.js` avoids re-fetching on every single page view, since reviews don't change minute to minute and Places API billing is usage-based. This is a soft cap, not a hard one — Vercel serverless functions can cold-start at any time, which clears the cache — but it's enough to smooth out bursts of traffic within a warm instance.
- **"Leave us a review" link is deliberately decoupled from the Place ID.** `writeReviewUrl()` prefers `GOOGLE_REVIEW_URL` — the "Get more reviews" share link from Business Profile Manager (business.google.com → the listing → "Get more reviews"/"Ask for reviews"), generated directly from the verified account, no Place ID or API call needed at all. It only falls back to building `https://search.google.com/local/writereview?placeid=...` from `GOOGLE_PLACE_ID` if `GOOGLE_REVIEW_URL` isn't set. **Why this split exists:** Sky House Cleaning's Business Profile recently moved address (Draper → Magna, UT → CA), and as of this writing the Places API's Text Search cannot find the listing at all — not by name, not by phone, not even with a location bias circled tightly on the exact coordinates pulled from the business's own canonical Maps URL (`https://www.google.com/maps/place/Sky+House+Cleaning/...`). Best guess is Google's search index hasn't fully caught up with the recent move. A wrong Place ID was briefly deployed as a result (found via Text Search, looked plausible, turned out to belong to a different, similarly-named competitor two towns over) and had to be pulled — don't repeat that mistake by trusting a Text Search result without verifying its `displayName` and phone number match. `GOOGLE_REVIEW_URL` sidesteps the whole problem for the review button specifically; the live-reviews widget below still needs a correct `GOOGLE_PLACE_ID` and falls back to curated testimonials until one's found. "See All Reviews on Google" (a separate button) uses `googleMapsUri` from the live API response, so it only appears when that fetch actually succeeds.
- **Star ratings:** `TestimonialCard.astro` grew an optional `rating` prop (rounded to the nearest whole star for display) — passed for live Google reviews, left `null` for the static fallback testimonials (which don't carry a numeric rating), so the component silently omits the star row in that case rather than showing something fabricated.

## Jobs (formerly Dispatcher)

Lives at `/admin/jobs`, same Basic Auth gate, no separate login yet (that's the per-cleaner phase below). `/admin/dispatch` is kept as a 301-redirect stub to `/admin/jobs` rather than deleted, so any old bookmark still lands somewhere — files can't be deleted from this project, only overwritten, so a redirect stub is the cleanup pattern going forward for any future page rename. The sidebar nav link and page title say "Jobs"; the underlying API routes are still under `/api/admin/dispatch/*` — renaming those too would've meant touching every fetch call in the file for zero user-facing benefit, so they were deliberately left alone.

Renamed after the business owner shared reference screenshots of Jobber's own Jobs list (client/job/property/schedule/status/total table with overview stat cards and Status/Job Type filters) and asked for it, noting that if something similar already existed it should just become "Jobs" rather than adding a second nav item — this page already read every job off the calendar, so it absorbed the new List view rather than a separate page being built.

**Architecture — deliberately NOT a duplicated `jobs` collection.** Google Calendar is already the source of truth for what's scheduled (bookings create/move real calendar events — see "Booking & payments architecture" above). Firestore only adds the dispatch-specific overlay: which cleaner(s) are assigned and what status the job is in. `src/lib/googleCalendar.js` gained `listEvents({ timeMin, timeMax })` to read a date range (filters out cancelled events and the transparent staff-reminder events from `createReminderEvent`). `src/lib/dispatch.js` handles the Firestore side: a `jobAssignments` collection and a `cleaners` collection.

**Why the job key is `${eventId}::${visitDate}`, not just the eventId:** recurring plans reuse the same calendar event, moving it forward to the next date each cycle (`updateBookingEvent`) rather than creating a fresh event every time. Keying by eventId alone would mean marking last week's visit "completed" stays stuck on this week's not-yet-done occurrence once the event moves. Folding in the visit's local date means each occurrence gets a clean "unassigned" default automatically, and past keys are left behind as a free history of completed jobs — see the comment at the top of `dispatch.js` for the full reasoning.

**Data model:**
- `cleaners` collection: name, phone, email, `active`, `firebaseAuthUid` (empty until the per-cleaner login phase below).
- `jobAssignments` collection, doc id = `jobKey(eventId, visitDate)`: eventId, visitDate, `assignedCleanerIds` (array), `status` (`unassigned` → `assigned` → `en_route` → `in_progress` → `completed`), `dispatchNotes`, `cleanerConfirmed` (boolean, default `false`).
  - **`cleanerConfirmed` is a manual staff toggle for now, not a real cleaner-side acceptance.** Named after the end state ("the cleaner has confirmed") rather than the current mechanism ("staff checked a box after calling them"), specifically so that once per-cleaner login exists (see "Not built yet" below), a cleaner tapping "Accept" in their own mobile view can just set this same field directly — nothing about the field, `update-job.js`, or anything that reads it needs to change, only who's allowed to flip it.
- **Staff-only fields living on the calendar event itself, not Firestore:** `amountPaid`, `jobType` (`one_time`/`recurring`), and `clientName`, written into `extendedProperties.private` on the Google Calendar event at booking time (`createBookingEvent()` in `googleCalendar.js`, called from both `checkout.session.completed` and the `invoice.paid` renewal path in `stripe-webhook.js`). **Why `.private` and not `.shared`:** Google Calendar's own API only ever returns private extended properties to the identity that created them (our service account) — never to any other calendar viewer, even one with full edit access. That's a hard guarantee from Google, not something this app enforces — so cleaners who are given calendar access to see their own schedule (a separate, human decision, outside this app's control) still can't see a job's dollar amount. This was a deliberate requirement, not an afterthought: the business owner explicitly asked for the Total column to stay admin-only. `list-jobs.js` reads these back via `event.extendedProperties?.private` and merges them into each job object; jobs booked before this existed simply won't have them (empty string, not an error — `/admin/jobs`'s List view shows "N/A" for `amountPaid` in that case, and falls back to parsing the client name out of the event summary text for `clientName`).

**UI:** `/admin/jobs` — a **List / Day / Week / Month** view switcher (`.admin-view-btn`), sharing one date-range-aware read (`/api/admin/dispatch/list-jobs.js`; the `days` query param cap was raised from 31 to 120 so List view's wider window fits in one request).

Redesigned twice: first after 15 reference screenshots of Jobber's Schedule board (Day/Week/Month calendar), then again after screenshots of Jobber's separate Jobs list (the default view now). The result:

- **List view** (default) is a flat, filterable/searchable table — closest to what the reference screenshots showed. Fetches a fixed 90-day rolling window (30 days back, 60 forward) in one read and computes everything client-side. A Job Type filter (All/One-off/Recurring/Quote-based, reading the `jobType` field) sits above a search box (matches client name, service, and property, client-side substring match) and a sortable table (Job #/Client/Service/Property/Schedule/Status/Total, click a header to sort/reverse). Clicking a row opens the same shared job-detail modal every other view uses. **Superseded by the section right below** — the Jobber-parity Overview/Status redesign — see that for the current behavior; kept here only as the "why List view exists at all" origin story.
  - Job number column, the shared modal, Day/Week/Month, cleaner management, and the sidebar badge/icons described below this bullet are all unchanged by that redesign.
- **A single shared job-detail modal** (`#job-modal-backdrop`/`openJobModal()`/`closeJobModal()`/`saveModalJob()`) is the *only* place a job gets edited — team assignment (multi-select), status, the "Confirmed by cleaner" checkbox, and a `dispatchNotes` textarea (auto-saves debounced 600ms), all hitting the same `/api/admin/dispatch/update-job.js`. All four views open this same modal rather than each having their own inline editing UI. Unassigning every cleaner from a job auto-unchecks (and saves) `cleanerConfirmed: false` — a confirmation with nobody assigned means nothing. Closing the modal reloads whichever view is open, since an edit can change any view's contents (and the sidebar badge, next page load).
- **Day view** is a full hour-ruler grid, one column per cleaner plus "Unassigned" (mirroring Jobber's own Day view layout). The hour range defaults to `WORKING_HOURS` (`src/data/booking.js`, 8am–6pm) and expands automatically if any job that day falls outside it. Only cleaners who are active, or who have a job that day despite being inactive, get a column. Jobs are positioned/sized by real clock time via `minutesSinceMidnightPT()` (an `Intl.DateTimeFormat` `hour12:false` read with a `% 24` guard, same pattern `reschedule.astro`'s `toTimeInputValue` uses) against a `HOUR_HEIGHT` (56px) pixel-per-hour constant. Clicking a block opens the shared modal. **Deliberate scope cuts, not oversights:** no drag-and-drop to reassign/reschedule (materially bigger build — pointer tracking, collision handling, touch support), and no overlap-avoidance layout for two jobs stacked on the same cleaner at the same time (rare for a small crew, so overlapping blocks just render overlapped rather than getting a real algorithm).
- **Week view** is a 7-column board; each job renders as a colored chip (`.admin-chip`, red-tinted via `.admin-chip--unassigned` when nobody's assigned) showing time, summary, assigned cleaner name(s) or "Needs cleaner," status badge, and a confirmed checkmark. Clicking a chip opens the shared modal; clicking a column's date header still jumps into Day view for that date (`jumpToDay()`).
- **Month view** is a calendar grid where each day cell shows small colored visit chips (one per job, not just a count) — red-tinted the same way for unassigned jobs. Clicking a chip opens the modal (`event.stopPropagation()` so it doesn't also trigger the day jump); clicking elsewhere in the cell (the date number) calls `jumpToDay()`.
- A collapsible "Manage cleaners" section at the top (shared across all four view modes) handles the roster (add + toggle active/inactive).
- Backed by `/api/admin/dispatch/list-jobs.js` (the merge), `update-job.js`, `list-cleaners.js`, `create-cleaner.js`, `update-cleaner.js` — no new API routes were needed for the List view; the existing endpoints already returned everything it needs.
- **Sidebar icons:** `AdminLayout.astro`'s nav items now each render a small hand-written inline SVG (24x24 stroke outline, no icon-library dependency) before the label, Jobber-style — see `ICONS` in that file.
- **Sidebar badge:** `AdminLayout.astro` fetches today's job list on every `/admin/*` page load (not just Jobs itself) and shows a small red count badge next to the "Jobs" sidebar link when any of today's jobs have no cleaner assigned — reuses the same `list-jobs.js` read Day view uses, just scoped to today. Fails silently (no badge, not an error) if the fetch fails, since it's a convenience indicator.
- **Job numbers:** every job created from now on gets a sequential, staff-facing number (`#1`, `#2`, …), shown as its own column in List view and in the job-detail modal's title. `getNextJobNumber()` (`src/lib/dispatch.js`) reads-and-increments a single Firestore counter doc (`counters/jobNumber`) inside a transaction — Firestore has no native auto-increment, this is the standard workaround, and the transaction is what stops two jobs created at the same instant from colliding on the same number. Called at every `createBookingEvent()` call site (both in `stripe-webhook.js`, and in `create-quote-job.js` below) and stored in that event's `extendedProperties.private.jobNumber`. Same graceful-degradation pattern as `amountPaid`/`jobType`/`clientName`: if Firestore isn't configured or the transaction fails, the job still gets created, it just has no number (shown as "—"), and there's no retroactive backfill for jobs that predate this.

### Jobber-parity List view redesign (Overview, Status filter, Archived, Action Required)

Built after the business owner shared a screenshot of Jobber's own Jobs page and asked for the same Overview/Status structure — a selectable Overview list of "attention needed" counts, plus a Status dropdown covering Active/Today/Upcoming/Late/Unscheduled/Action Required/Requires Invoicing/Archived. Each status was checked against Jobber's own help-center docs (`Jobs List Page and Key Metrics`) rather than guessed at, which is what surfaced two corrections worth knowing:

- **"Ending Within 30 Days" was deliberately left out.** Jobber's version means a job's own built-in duration is about to lapse — a concept this app has no equivalent of, since a recurring plan here just bills indefinitely until someone cancels it. The only "end date" this app ever has is `cancel_at`, which staff set by hand via Manage Plans when a client has *already* asked to cancel — so a stat built on it would only ever flag clients who've already told you they're leaving, never give an early warning the way Jobber's version does. Not worth building for that reason.
- **"Action Required" and "On Hold" are the same status, not two.** Jobber's own docs describe Action Required as "jobs that are still active but have no more upcoming visits… think of action required like being on hold" — there's no separate "On Hold" entry in their actual status list. This app builds exactly one real concept for it (below), not two overlapping ones.

**Overview card** (`#overview-list`, `.admin-overview-list__item[data-filter]`) replaces the old 4-card grid with a selectable list — Late / Requires Invoicing / Action Required / Unscheduled, plus **Needs a Cleaner** as a fifth, non-Jobber bonus line (kept because it's genuinely useful dispatch-specific info Jobber has no equivalent for, being a single-business tool without per-cleaner scheduling). Clicking a line sets the same `listStatusFilter` the toolbar's Status `<select>` controls — kept in sync in both directions (`applyListFilters()` toggles `.is-active` on the matching `<li>`, and clicking an `<li>` also updates `listStatusFilterEl.value`). Recent Visits / Visits Scheduled stay as their own two cards alongside it, unchanged from before.

**Status `<select>`** now has two `<optgroup>`s: a Jobber-style group (Active/Today/Upcoming/Late/Unscheduled/Action Required/Requires Invoicing/Archived) and the original "Cleaner status" group (Unassigned/Assigned/En route/In progress/Completed) — nothing from the old per-visit dispatch workflow was removed, the new options were added alongside it. "Active" is Jobber's own word for "in progress," so it maps to the exact same `job.status === "in_progress"` check the Cleaner-status group's "In progress" option also uses — two labels, one predicate, both kept since staff know both vocabularies now. The "Unassigned"/"Needs a Cleaner" filter checks `assignedCleanerIds.length === 0` directly rather than `job.status === "unassigned"` — those two can drift apart (unassigning every cleaner from an already-`assigned`/`en_route` job only resets `status` back to `"unassigned"` when cleaners go from zero to some, not the other way — see the `modalAssign` change handler), so checking the real array is what keeps the Overview count and the filtered rows always agreeing.

**Archived** (`archived: false` default on `jobAssignments` docs in `dispatch.js`, accepted as a boolean in `update-job.js`) is a pure visibility flag, nothing else — doesn't touch billing or the calendar event. Toggled from the job-detail modal's "Archive job"/"Unarchive job" button. Hidden from every filter except the explicit "Archived" one (checked first in `matchesStatusFilter()`, before the `filter === "all"` branch, so "All" never shows archived jobs either — matching Jobber's own default-list behavior).

**Requires Invoicing** cross-references the Invoices feature (see below) rather than adding new state: `loadListView()` fetches `/api/admin/invoices/list.js` alongside the jobs read and flags any job whose `jobKey` has an invoice that isn't `paid` or `void` yet (draft, sent, or overdue all count). No new data — this is purely a join done client-side at read time.

**Unscheduled** surfaces accepted-but-unscheduled quotes (see "Requests, Assessments & Quotes" above) as pseudo-rows in the same table — `isUnscheduled: true`, no `eventId`/`jobKey` since no calendar event exists yet for these. Fetched from `/api/admin/quotes/list.js?status=accepted` alongside the jobs read. These rows only ever match the "All" or "Unscheduled" filters (checked first in `matchesStatusFilter()`), get excluded from the Recent Visits/Visits Scheduled date-window math (no `visitDate` to bucket them by), sort to the end under ascending "Schedule" sort (`Number.POSITIVE_INFINITY` fallback in `listSortValue()` since there's no real `start` time), and clicking one navigates to `/admin/crm/quotes` instead of opening the shared job-detail modal — that page already has the real "Schedule Job" action, deliberately not duplicated here. `serviceLabel` on each pseudo-row comes from `QUOTE_SERVICE_TYPES` (passed into the page via a `data-quote-service-types` attribute, same pattern `book-quote.astro` and `quotes.astro` use), since there's no calendar event summary to parse a service name out of the way real rows do.

**Action Required** is the one piece with real weight: putting a recurring client's plan "on hold" actually pauses their Stripe subscription, not just a label. Two new endpoints:
- **`/api/admin/subscriptions/list-paused.js`** — fetches every Stripe subscription (same full-roster approach `/admin/minimum-commitments.astro` uses) and filters for `sub.pause_collection` being set on a still-live (`active`/`trialing`) subscription. A paused subscription's `status` field doesn't change to anything special — pausing only ever touches `pause_collection`, never `status` — so that field is the only reliable signal.
- **`/api/admin/subscriptions/toggle-hold.js`** — `POST {hold: true, clientEmail}` looks up the client's subscription by email (same `stripe.customers.list({email})` → `stripe.subscriptions.list({customer})` pattern `find-subscriptions.js` uses for Manage Plans) and sets `pause_collection: {behavior: "void"}`, meaning Stripe generates no invoice at all while paused — no charge, and critically, no `invoice.paid` webhook fires either, so `stripe-webhook.js`'s renewal branch never creates the plan's next calendar visit while on hold. `POST {hold: false, subscriptionId}` clears it (`pause_collection: ""`) to resume normally. Deliberately uses the older, stable `pause_collection` field rather than Stripe's newer dedicated pause/resume endpoints, which are still preview-API-only as of this writing — not something to build live billing logic on for a production account.
- Staff put a plan on hold from the job-detail modal (a "Put client's plan on hold" button, shown only when `job.jobType === "recurring"`, using the job's `clientEmail` — a new field on `list-jobs.js`'s response, read straight from the calendar event's real Google Calendar attendee rather than private metadata, so it's available retroactively on every recurring job ever booked, not just new ones). Taking a plan off hold happens from the **Action Required panel** — a second table (`#action-required-panel`) that replaces the jobs table entirely when that filter is selected (there's nothing to show as table *rows*: a paused plan by definition has no upcoming visit), listing each paused client with a Resume button.
- Nothing about the already-existing current/next calendar visit changes when a plan goes on hold — if staff also want that visit cancelled, that's the separate, existing "cancel a specific visit" tool, not something a hold does automatically.

**Not built yet:** per-cleaner Firebase Authentication (Email/Password sign-in provider still needs enabling in the Firebase console — see the CRM setup notes above) and the phone-friendly crew view where a cleaner logs in, sees just their own day, and taps to actually confirm/accept a job themselves (which would then set the same `cleanerConfirmed` field the manual staff toggle sets today). Today, only admin/staff (via the shared Basic Auth) can see or edit the jobs board.

### Schedule (split from Jobs)

Lives at `/admin/schedule`, its own sidebar nav entry (first of the flat links, ahead of Jobs and Invoices — see `flatLinks` in `AdminLayout.astro`), same Basic Auth gate. Built after the business owner shared 8 screenshots of Jobber's separate Schedule page (Month/Week/Day calendar, Type/Team/Status checkbox filters, and a two-step click-to-view flow: a small popup on the calendar with Edit/Details buttons, branching into a full Edit Visit form or a full Visit Details view) and asked for the same thing, framed as its own tab rather than folded back into Jobs.

**Why a separate page instead of adding this onto Jobs:** Jobs had already absorbed Day/Week/Month once (see "Jobber-parity List view redesign" above), but doing so again with checkbox-multiselect filters and a two-tier popup system would mean two very different interaction models — flat filterable table vs. calendar-with-modals — competing for the same page. Jobber itself keeps these as separate top-level pages, so this app now does too: **Jobs stays List-only** (the day-to-day "what needs attention" table), **Schedule owns Month/Week/Day** (the day-to-day "who's where, when" calendar). `jobs.astro` had its view-switcher, period-nav, Day/Week/Month markup and CSS, and the "Manage cleaners" section all removed (they moved to `schedule.astro` verbatim) — its shared job-detail modal, List view, Overview/Status filtering, and everything else from the redesign above is unchanged.

**Same read-model as Jobs, still no duplicated `jobs` collection.** `schedule.astro` calls the same `/api/admin/dispatch/list-jobs.js` Google Calendar + `jobAssignments` merge Jobs uses — Schedule is a second view over the same data, not a second data model. Cleaner roster management (add + toggle active/inactive) moved here wholesale from Jobs, since assigning cleaners to visits is squarely a Schedule-page task now.

**Type / Team / Status filters** are checkbox-multiselect popovers (`setupFilterPopover()`), not `<select>` dropdowns like Jobs' Status filter — these three combine with AND logic (e.g. "Recurring" + "Maria" + "Unassigned" all at once), which a single-value dropdown can't express. Each popover button shows `Label | summary`, where summary is "All" if every option is checked, "None" if none are, the one checked label if exactly one is, or "N selected" otherwise. Type mirrors the `jobType` field (One-off/Recurring/Quote-based); Team lists active cleaners plus "Unassigned"; Status reuses the same Jobber-parity vocabulary as Jobs' dropdown (Active/Today/Upcoming/Late/Unscheduled/Action Required/Requires Invoicing/Archived) rather than inventing a second one.

**Visit cards, not truncated pills.** Month view (`.admin-month-chip`) and Week view (`.admin-chip`) both render each visit as a small rounded card — a circular initials avatar (`initials()`, first letter of up to the first two words of the assigned cleaner's name, or "—" for unassigned) next to a bold start time and the visit summary, matching the reference screenshots of Jobber's own calendar cards. Text wraps rather than getting cut off with an ellipsis — the card grows taller instead. Two bugs surfaced and got fixed while building this: (1) `.admin-month-day` (the grid cell) needed an explicit `min-width: 0` — grid items default to `min-width: auto`, so a cell with a long unbroken visit label was stretching its whole day-of-week column wider than its `1fr` share, throwing off every other column's alignment with the SUN–SAT headers (same overflow gotcha as `AdminLayout.astro`'s `.admin-main` comment). (2) `.admin-chip` (the Week board's visit card) had no CSS at all — a gap from the original single-file build that had gone unnoticed until this pass; it now shares the same blue/red assigned/unassigned color language as the Day view's `.admin-daygrid__block`.

**Two-tier click interaction**, deliberately separate from — and not applied to — Jobs' existing single combined job-detail modal:
1. Clicking a calendar chip/block opens a small centered **Visit Popup** — a quick-glance summary (client, service, time, assigned cleaner(s)) plus a Completed checkbox, a ••• More menu (Archive/Unarchive, Put on Hold/Resume — reusing the exact same endpoints the Jobs modal uses), and two buttons: **Edit** and **Details**. Jobber's popup also has a "Find a Time" action; left out entirely per the business owner ("that feature, I don't think I need right now") — no disabled placeholder button, just not built.
2. **Edit** opens a full **Edit Visit** form — date, start/end time, instructions/notes, and team assignment. **Details** opens a full **Visit Details** view with tabs (Client, Notes, Info) and a Mark Complete action plus a More-actions menu (Edit, and the same Archive/Hold actions as the popup). Team reminders (text/email) shown in Jobber's own Details screen were deliberately left out — the business owner called them "maybe a later task" — again, no placeholder UI for them, just absent. Line items were also left out per the same scoping conversation.

**Recurring vs. non-recurring is a hard scope boundary on the Edit Visit form, not a cosmetic one.** A recurring plan's visit already has its own dedicated, subscription-aware tools (`reschedule-subscription.js` / `cancel-visit.js` / `cancel-subscription.js`, all under Manage Plans) that keep a Stripe subscription's `lastVisitStart`/`lastVisitEnd`/`lastEventId` metadata and `trial_end` billing alignment in sync when a visit moves. A generic "move or delete any visit" tool built for Schedule must never touch a recurring visit's date/time/existence directly, or that billing math silently desyncs. So on the Edit Visit form: for a `recurring` job, the date/start/end fields are shown read-only with a note pointing to Manage Plans for rescheduling, and the Delete button is disabled with an explanatory tooltip. For `one_time`/`quote_based`/`assessment` jobs, both are fully live, backed by two new endpoints:
- **`/api/admin/dispatch/reschedule-visit.js`** — moves a single visit's date/time via `updateBookingEvent`. Because `jobKey` is `${eventId}::${visitDate}` (see the Jobs section above), moving a visit to a *different* date produces a genuinely different key — without migration, the visit would silently lose its assigned team/status/notes/archived flag on next load (a fresh key reads back as an all-default doc). The endpoint handles this by copying the old key's `jobAssignments` doc forward to the new key whenever the date actually changes; same-day time-only edits skip this since the key is unchanged. Calendar-succeeded-but-Firestore-carryover-failed is treated as a non-fatal warning, same tolerance every other split write in this app has.
- **`/api/admin/dispatch/delete-visit.js`** — permanently removes a one-off/quote-based/assessment visit from both the calendar and its Firestore doc. Never reachable for recurring jobs (button disabled client-side, and nothing routes a recurring job's eventId here).

**Not built (deliberate, not deferred by accident):** "Find a Time" availability search, text/email visit reminders to the team, and line items on a visit — all explicitly scoped out per the business owner's own framing above rather than stubbed as disabled buttons.

## Requests, Assessments & Quotes

**Superseded the old single "book a quote job immediately" flow described in earlier revisions of this file.** Reworked after the business owner asked, in effect, "what's the actual workflow — do I book the cleaner at Request time or at Quote time?" Rather than guess, this was researched against how Jobber itself (the tool the reference onboarding screenshots came from) structures the same problem: Requests and Quotes are separate list pages, a Request can optionally book a real on-site-assessment visit before any price is set, and converting a Request → Quote → Job never auto-fires a calendar event — each stage is a deliberate, separate action. Two decisions came out of that research and the owner's own answers: (1) a Request's assessment should book a **real** calendar slot with an assigned cleaner, not just an availability glance; (2) Quotes needed to become a genuinely separate step — price sent, customer accepts + pays a deposit, *then* staff schedule the real job — rather than the old flow's "quote creates the job immediately, deposit just gates the money."

**The pipeline, end to end:** Request (`deals` doc, `stage: "new_inquiry"`) → optionally, **Schedule Assessment** (real calendar visit + assigned cleaner) → **Send a Quote** (price + deposit terms, no calendar event yet) → customer reviews and pays the deposit → **Schedule Job** (staff pick the actual date/time; this is the only point a calendar event/job now gets created for quote-based work). Two Firestore collections carry this: `deals` (the Request/lead pipeline, unchanged collection from CRM v1, just gained the `assessment` field) and a new `quotes` collection (`src/lib/quotes.js`) for the formal, customer-facing price. They're linked by `deal.id` ↔ `quote.dealId`, but a quote doesn't strictly require a deal (book-quote.astro also works with no `?dealId=`, for a quote with no prior Request on file).

**`/admin/crm/requests`** (nav: CRM → "Requests") — the Request inbox, forked from the old combined Deals board, scoped to `stage: "new_inquiry"` only. "+ Add a request" is the same pick-existing-or-create-inline contact form the old Deals page had. Each card has **Schedule Assessment** (opens a modal: date, time, multi-select cleaner picker sourced from `/api/admin/dispatch/list-cleaners.js`, posts to `/api/admin/crm/schedule-assessment.js`), **Move to Quotes** (advances `stage` to `quote_sent`), and **Mark Lost**. `/api/admin/crm/schedule-assessment.js` books a real calendar event via `createBookingEvent()` (`privateMetadata: {jobType: "assessment", clientName}` — so an assessment visit is visible on `/admin/jobs` like any other calendar item, just tagged distinctly from a real job) plus a `jobAssignments` overlay doc for cleaner dispatch, then writes `deal.assessment = {scheduled: true, completed: false, eventId, visitDate, cleanerIds}`. A card whose assessment is already scheduled shows a "📋 Assessment scheduled — <date>" line and the button relabels to "Reschedule Assessment." Assessment completion itself isn't tracked separately yet — it just shows up as a normal calendar item staff can see happened.

**`/admin/crm/quotes`** (nav: CRM → "Quotes", icon reused from the old "Quote-Based Job" entry) — two sections on one page:
- **Formal Quotes** — every doc in the new `quotes` collection, filterable by status (`pending`/`accepted`/`scheduled`/`declined`+`expired`), fetched from `/api/admin/quotes/list.js`. A `pending` quote gets a "Copy Customer Link" button (`/confirm-quote/[id]`); an `accepted` quote (customer paid the deposit, no job yet) gets **Schedule Job**, opening a date/time/estimated-hours modal that posts to `/api/admin/quotes/schedule.js` — the same endpoint, same form shape as the old immediate-booking flow used to have, just moved to fire after acceptance instead of at quote-creation time.
- **Deal Pipeline** — deals still in `quote_sent`/`follow_up` stage (the informal, pre-formal-quote pipeline carried over from the old Deals board), each with **Send Formal Quote** (→ `/admin/book-quote?dealId=<id>`, which prefills the form from the deal+contact), **Convert to Booking** (unchanged — for standard-priced services with a real catalog price, skips the formal-quote step entirely), **Move to Follow-Up**, **Mark Won**, **Mark Lost** — same actions and API calls (`update-deal.js`, `win-deal.js`) the old Deals board had.

**`/admin/book-quote`** ("Send a Quote," reached only via the Quotes page now — no longer a top-level sidebar item, see `AdminLayout.astro`'s `activeMatch` comment) is where staff type in the quoted total and deposit terms for the three services with no catalog price: **Office & Commercial Cleaning**, **Garage Cleaning & Organization**, and **Post-Construction Cleaning** (`QUOTE_SERVICE_TYPES` in `src/data/booking.js` — confirmed by reading each service's own page, all three say pricing is custom/quote-based, and `calculatePrice()` in `pricing.js` has no branch for any of them). **No date/time fields anymore** — that's the core change from the old flow. `?dealId=` in the URL prefills service type/name/phone/email/address/notes by fetching `/api/admin/crm/list-deals.js` and reverse-matching the deal's `serviceType` label to its `QUOTE_SERVICE_TYPES` key.

- **`src/lib/quotes.js`** (new, supersedes `pendingDeposits.js` for this flow) — `QUOTE_STATUSES = ["pending", "accepted", "declined", "expired", "scheduled"]`, `QUOTE_EXPIRY_DAYS = 14` (same reasoning `PENDING_DEPOSIT_EXPIRY_DAYS` used to have — give the customer real time, not pressure). `createQuote()` stores `dealId`, `serviceType`, `customer` (name/phone/email/address), `quotedTotal`, deposit terms/amount, `notes`, and empty `jobKey`/`eventId`/`visitDate` placeholders that `markQuoteScheduled()` fills in later. **No calendar event exists at creation** — that's the whole point of the split.
- **`/api/admin/quotes/create.js`** (replaces `/api/admin/create-quote-job.js`, which is now an HTTP 410 deprecation stub pointing here — same "can't delete, only overwrite" pattern used everywhere else in this file): validates the form, computes `depositAmount` server-side from the quoted total (never trusts a pre-computed number — same principle `calculatePrice()` uses, just applied to a manually-entered total), calls `createQuote()`, and returns a `/confirm-quote/[id]` link for staff to send the customer. Creates no calendar event and holds no calendar slot.
- **`/confirm-quote/[id].astro`** mirrors `/confirm-deposit/[id].astro`'s public, no-auth, server-rendered pattern, with one visible difference: no Appointment card, since no date exists yet — just Service, Your Details, an agreement checkbox, and a Quote Summary sidebar.
- **`/api/confirm-quote/finalize.js`** creates an ad-hoc Stripe Checkout Session for the deposit (`price_data`, same reasoning as `/api/confirm-deposit/finalize.js` — the amount was already fixed server-side, the customer's browser never sends a dollar figure), `metadata: {quoteId}`, success URL `/confirm-quote/success`.
- **`stripe-webhook.js`** gained a `metadata.quoteId` branch (distinct key from `depositId`/`pendingBookingId`/`invoiceId` so none of the four flows can collide) calling `markQuoteAccepted()` — flips the quote to `accepted`, still creates no calendar event.
- **`/api/admin/quotes/schedule.js`** is the only place in this entire flow that creates a calendar event. Requires `quote.status === "accepted"`; staff pick a real date/time/estimated-hours; it assigns a job number (`getNextJobNumber()`), creates the calendar event with the same `privateMetadata` shape the old immediate-booking flow used (`jobNumber`, `clientName`, `jobType: "quote_based"`, `serviceType`, `quotedTotal`, `depositAmount`), upserts a `jobAssignments` doc with `depositStatus: "paid"` (the deposit was already collected before this step could even run), and calls `markQuoteScheduled()`. From this point on, the job behaves identically to the old flow's quote-based jobs everywhere downstream — same Jobs List/Day/Week/Month display, same "Total: quoted amount, Deposit paid ✓" treatment, same invoice-reminder-on-completion behavior described below.
- **Where a scheduled quote's job shows up on `/admin/jobs`:** identical to before this rework — `jobType: "quote_based"` in the List view's filter, Total column showing `quotedTotal` with a deposit-status line underneath, `quotedTotal`/`depositAmount` fixed on the calendar event's `extendedProperties.private`, `depositStatus` mutable in the Firestore overlay. Nothing about that display logic changed, only how a job gets to that state.
- **What this doesn't do:** track assessment completion as its own explicit step (an assessment visit is just a calendar item, same as any job); auto-fill quote line items from the Request's own notes (deliberately not done, matching Jobber's own behavior of showing the source record in a reference drawer rather than silently copying fields — though this app's `?dealId=` prefill on `book-quote.astro` is a smaller, deliberate exception: it prefills the *form*, staff still review/adjust before sending).

**Reminder to invoice the remaining balance:** `/api/admin/dispatch/update-job.js` (the same endpoint the shared job-detail modal already calls to save status changes) checks, on the specific transition into `status: "completed"`, whether the job is quote-based, its deposit was already paid, and it hasn't been reminded about before (`invoiceReminderSent` on the `jobAssignments` doc — set the first time the reminder fires, so re-saving or toggling status never double-reminds). If a positive remaining balance exists (`quotedTotal - depositAmount`), it drops a private, non-blocking reminder event on the business calendar via the existing `createReminderEvent()` helper (`googleCalendar.js`) — the same mechanism `stripe-webhook.js` already uses for "customer hit their minimum commitment" notifications, so no new notification channel was needed. The reminder's summary/description spell out the client, quoted total, deposit already collected, and the exact balance still owed. A new `getBookingEvent({ eventId })` helper (`googleCalendar.js`) reads the job's calendar event back to check these values authoritatively (jobType/serviceType/quotedTotal/depositAmount, all in `extendedProperties.private`) rather than trusting whatever the admin UI happened to have loaded in memory. Entirely best-effort/non-fatal, like every other reminder in this codebase: if it fails, the status change itself still saves. **This same code block also creates the actual Invoice record described below** — same gate, same non-fatal handling, so nothing about this reminder changed, it just gained a sibling.

## Invoices

Tracks and collects the remaining balance on quote-based jobs, closing the gap the previous section's "doesn't do" note used to describe. Built after the business owner saw Jobber's Requests/Quotes/Jobs/**Invoices** pipeline and asked for the one piece genuinely missing here — Requests and Quotes already existed in some form (the CRM's Deals pipeline, reshaped above), Jobs already existed, only real billing-collection tracking didn't.

**Data model:** a single `invoices` collection (`src/lib/invoices.js`), doc fields: `jobKey`/`eventId`/`visitDate` (ties back to the job), `jobNumber`, `clientName`/`clientEmail`/`clientPhone`, `serviceType` (a `QUOTE_SERVICE_TYPES` key), `amount`, `notes`, `status` (`draft` → `sent` → `paid`, or `void`), `dueAt`, `sentAt`/`paidAt`, `stripeSessionId`, `paymentMethod` (`"stripe"` or `"manual"`, the latter for a check/cash/phone-card payment marked paid by hand). **`overdue` is never a stored status** — `listInvoices()`/`getInvoice()` compute it at read time as an `effectiveStatus` field (`sent` + past `dueAt`) and return that alongside the real `status`, the same "don't write what you can compute at read time" reasoning `PENDING_DEPOSIT_EXPIRY_DAYS` uses in `pendingDeposits.js`. This also means there's no cron/scheduled task involved anywhere in this feature.

**How an invoice gets created — automatically, not by hand:** the exact same `update-job.js` code block described in "Reminder to invoice the remaining balance" above also calls `createInvoice()`, seeded with the job's `quotedTotal - depositAmount` as a **draft**. Draft (not auto-sent) is deliberate — actual hours on an estimate-based job can run over/under, so staff get a chance to review or adjust the amount before a customer ever sees it. Contact info (`clientEmail`/`clientPhone`) isn't available on the calendar event's own private metadata (only `clientName` is — see the Jobs section above), so this lookup calls `getQuoteByJobKey()` in `src/lib/quotes.js` (a `.where("jobKey", "==", ...)` query — there's always at most one quote per quote-based job) rather than adding more fields to the calendar event just for this one read. This used to call `getPendingDepositByJobKey()` in `pendingDeposits.js` before the Requests/Quotes rework above replaced that data source; `pendingDeposits.js` still exists but is no longer written to by any current flow.

**`/admin/invoices`** (sidebar, flat link next to Jobs) is the staff view: overview cards (Drafts / Awaiting Payment + $ / Overdue + $ / Paid This Month $), a status filter row, and a table (Job #, Client, Service, Amount, Status, Due, Actions). Per-row actions depend on status: draft/sent get **Edit Amount** (a `prompt()`, same lightweight pattern as Deals' "Mark Lost" reason — not worth a modal for an occasional one-field edit), **Send** (draft) or **Copy Link** (already sent), **Mark Paid** (manual/offline payment), and **Void**; paid/void rows just show their end state, no actions. Backed by `/api/admin/invoices/list.js`, `update.js` (amount/notes/dueAt/void), `send.js` (draft → sent, hands back the public pay link), and `mark-paid.js` (manual payment, distinct from the Stripe-driven path below). Sidebar badge (`AdminLayout.astro`) shows a red count of invoices whose `effectiveStatus` is `overdue` — the only state that actually needs someone's attention, same reasoning as the Jobs "unassigned today" badge.

**Getting paid — mirrors the deposit flow exactly, one step later in the job's life:** "Send" generates `/pay/[id]` and copies it to the clipboard for staff to text/email by hand (no SMS/email provider is wired into this app — see the Privacy Policy's Third-Party Services list). **`/pay/[id].astro`** (public, no admin auth) shows the amount due and a "Pay Now" button — no agreement checkbox like `/confirm-deposit/[id]` needs, since the customer already agreed to the job and its price when they booked; this page is purely "here's what you still owe." **`/api/pay/create-session.js`** builds an ad-hoc Stripe Checkout Session (`price_data`, not a catalog price) from the invoice's own `amount` — same "staff already fixed this number server-side, the customer's browser never sends a dollar figure" reasoning as `/api/confirm-deposit/finalize.js`. **`stripe-webhook.js`** gained a new `metadata.invoiceId` branch in `checkout.session.completed` (a distinct key from `depositId`/`pendingBookingId` so the three flows can't collide) that calls `markInvoicePaid()` — unlike the deposit branch, this one touches no calendar event or job status, since the job is already `completed` by the time an invoice exists at all. `/pay/success.astro` mirrors `/confirm-deposit/success.astro` (verifies the session server-side before showing an amount).

**What this doesn't do:** send the pay link itself (staff copy/paste it into a text or email by hand, deliberately — see above), partial payments (an invoice is paid in full or not at all), or automatic late-fee/reminder escalation once something goes `overdue` beyond showing the sidebar badge.
